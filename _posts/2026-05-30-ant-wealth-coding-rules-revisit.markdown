最近翻相册时翻出一张老照片——蚂蚁财富工区某面墙上挂的"财富编码军规"海报，蓝底，十二条编号，第一条就是熟悉的 **"并发控制——一锁二判三更新，乐观引入须谨慎"**。我盯着这张照片看了一会儿，居然觉得有点恍惚——明明已经离开蚂蚁好几年，明明现在每天打交道的对象是无人车、是仿真平台、是路测日志，可那十二条规矩竟然一字不漏地在脑子里复述了出来，像一段刻进 DNA 的东西。

那年我在 **财富事业群做养老基金的 QA Owner**，后来也接了 **个人养老金** 这个国家级项目的质量护航。回过头看，那段日子留给我最深的不是某个具体的故障复盘，也不是某次双 11 上线时的肾上腺素，而是这套"军规"背后蕴含的一种 **金融级工程师的姿态**——**对系统的敬畏，对资金的敬畏，对用户每一分钱的敬畏**。

今天想把它重新读一遍。不是抄写，而是用今天的视角、把当年踩过的坑和当时来不及说清楚的体会一起写下来。

<!-- more -->

## 一、第一次被"金融级"四个字按在地上摩擦

我是从百度跳到蚂蚁的。来之前在核心搜索部门做 VUI 架构的测试开发——VUI 是搜索结果从后端渲染到前端页面的那一层中间架构，每天扛着百度首页搜索的全量流量，模板上千、卡片几十类、QPS 高到离谱，前端展现出一点点异常都是大事。也算见过世面——海量 QPS、长链路渲染、模板灰度发布的边界条件，没少熬夜处理过线上问题。所以最初拿到蚂蚁财富 QA Owner 这个角色时，心里其实是有点傲气的：业务再复杂，能比扛着搜索全量流量的渲染中台还复杂吗？

入职第三周，这点傲气就被现实磨平了。

那是我第一次完整跟一笔资金链路——用户在支付宝养老专区点了一笔基金申购，钱从用户余额扣到中间过渡户、再清结算到基金公司、再到份额确认、再到回写用户持仓——**这条链上居然横跨了七八个系统、十几次跨库事务、三组对账核对、一套幂等保护、一份资金安全核对**。每一跳都不是普通的 RPC 调用，而是带着 **xts 分布式事务、悬挂监控、空回滚校验、最终一致性兜底** 的一整套金融级仪式感。

我至今记得做新人串讲那天，我刚把这条链路在白板上画完、自以为讲得还算清楚，主管放下手里的咖啡杯，盯着白板上那条线问我：

> "这笔钱在系统里看起来每一秒都在某个地方'流动'，但你告诉我，**你能不能在任意一秒回答出来：这笔钱现在到底归属于谁？**"

我答不上来。后来花了大半个月才搞清楚答案——金融系统里"钱"从来不是某一行代码里的一个变量，而是 **同一时刻分布在多张库表里的、由 N 套核对规则共同维系的一个不变量**。这跟"功能正确"是完全不同的两件事。

军规第一条"并发控制——一锁二判三更新"，乍看像是给研发同学的，其实**对 QA 才是最致命的**：因为它意味着我们要测的不再是"这个接口返回是不是对的"，而是 **"在最极端的并发场景下，这个不变量还成不成立"**。这种心智模型的切换，是我后来做任何金融级业务的真正起点。

## 二、那张海报上的十二条，每一条背后都有故事

军规的版本我记得有几次更新，最经典的一版是按 **基础编码 → 架构设计 → 资金安全 → 中间件 → 数据质量 → 生产变更 → 应急止血 → 客户端前端** 八大类来组织的。我想分几个我印象最深的点聊。

### 「一锁二判三更新」——这不是模板，是血泪

很多团队学这条规矩时，会把它变成一个机械模板：先 select for update、再判断状态、再 update。但当年在养老基金业务里我亲眼见过：**一个看起来标准的"一锁二判三更新"代码，因为 SQL 没走索引，select for update 锁住了一整张表**——结果周四早高峰直接把核心库锁死，影响面一路蔓延到上游。

那次复盘让我第一次真正理解"军规"为什么写到第六条又来一个"SQL 必须带字段，where 条件有索引，索引不含隐式转"——**这八条"基础编码"军规不是孤立的，它们彼此之间是网状关系**。并发控制依赖 SQL 性能、SQL 性能依赖索引设计、索引设计又依赖类型一致……任何一环松动，整套防御都垮。

后来再做评审，我自己慢慢养成一个习惯：**审到 select for update 一定会顺着 where 条件再追一层执行计划**。这个习惯到现在做无人车的车端日志审查也还在用——"看一处时一定要看它依赖的另一处"。

### 「乐观锁须谨慎」——一个被乐观锁咬过的下午

军规里那句"乐观引入须谨慎"很克制，但当年是真有人栽过。某个非主链路的小服务为了性能用了乐观锁版本号控制，跑了大半年都没事。直到某次营销活动开闸，瞬时并发把版本号冲突率拉到一个很高的值，**应用层重试逻辑写得又不够防御**——结果一波数据被反复覆盖，最后用户看到的余额对不上账。

那次问题的修复其实不大，但写复盘报告时业务老板问的一句话我记到现在：**"我们当初评估这个改动时，有没有人画过冲突率随业务增长的曲线？"**

没有。当时只评估了"功能正确性"和"性能收益"，没人评估"业务量到达某个阈值后乐观锁的失效曲线"。这件事在我后来的每一次方案评审里都变成了一个固定的检查项——**任何性能优化方案，必须给出失效边界**。

### 「幂等」——在金融系统里是空气，没了就死

幂等这条军规我后来觉得，是整个金融系统里最容易被低估的一条。研发同学经常说"我加了幂等表，搞定了"。但 QA 视角看下去，幂等的复杂度永远在边界条件里：

- **幂等字段是不是单一**？有没有上下游对幂等字段的理解不一致？
- **幂等返回是什么**？返回成功、还是返回上一次结果、还是返回幂等错误码？
- **异常场景幂等怎么处理**？下游不明确成功失败时，能不能给上游返回"未知"？
- **跨系统的幂等链路**？一个请求经过 A→B→C 三跳，每一跳的幂等键怎么对齐？

养老基金这条业务我记得对幂等做过一次专项治理，把全链路上每一个幂等点都列出来，一个个核对幂等键、幂等返回、异常场景。**那次治理结束时画的那张幂等矩阵图，我今天回到无人车业务去做"指令幂等"时还在沿用同样的方法**——指令重复下发到同一辆车上，会不会产生副作用？这其实和"申购请求重复提交"是同一个抽象问题。

军规的价值，正是在这些跨场景的抽象上凸显出来的。

## 三、第一次见到这么多自建中间件，我整个人是麻的

聊蚂蚁的工程文化，绕不开它那套自建的金融级中间件矩阵。我入职那会儿，每天打开内部知识库看到的全是缩写：**SOFA、SOFAStack、SOFABoot、SOFARPC、SOFAMQ、SOFATracer、Tair、OceanBase、ZDAL、DRM、Guardian、xts、LDC、AntVip、九州……**

刚开始我是真的麻了。麻不是因为多——别的大厂中间件也多——而是因为 **每一个组件都不是简单的"开源替代品"，而是为了某个金融级问题专门长出来的**：

- **OceanBase + ZDAL** 解决的是金融级数据库的一致性 + 分库分表透明化，不是简单的"分库代理"
- **Tair** 解决的是金融级缓存的高可用，主备切换、热点保护、容灾都做到极致
- **xts** 解决的是分布式事务的"悬挂"和"空回滚"问题，这两个名词当年我学了大半个月才搞明白
- **LDC（Logical Data Center）** + Gzone/Rzone/Czone 这套分区是为异地多活专门设计的，三地五中心 + RFO 库的恢复机制基本是工程级的艺术品
- **DRM + 九州** 配合做配置推送和变更管控，"推前内容勤比对"这条军规背后是无数次配置故障的血
- **Guardian 限流** 把令牌桶 / QPS 计数 / 熔断这些理论概念做成了工程上的开关

我至今记得有次一位中间件团队的同学给我们做内训，讲到 OceanBase 的"频繁写删表容易导致执行计划走错"——所以军规里要求 **"OB 设计中需要指定 HINT，且 HINT 中表应该设置为别名方式以保证 ZDAL 分库分表替换"**。当时我作为一个刚来三个月的 QA，听到这种细节级的工程约束时是真的肃然起敬——**这不是文档级的最佳实践，这是从生产故障里直接长出来的肌肉记忆**。

后来我自己审 SQL 时，看到 OB 表没带 HINT 别名都会条件反射地标红。这种条件反射不是培训培出来的，是被那张军规海报、被一次次的复盘会、被工区茶水间的工程师文化一点点浸出来的。

## 四、双 11 作战值班——那种紧张又兴奋的感觉，至今都很怀念

聊蚂蚁的那段时光，有一件事不能不提——**双 11 作战**。

财富业务在双 11 是相对边缘的（毕竟主战场是支付主链路 + 电商），但养老基金、理财、基金申购这些场景同样会承受流量洪峰。第一次参加双 11 作战值班时，我提前一周就开始紧张——全链路压测要复盘三轮、应急预案要演练四遍、限流配置要逐条 review、Tair 容量要提前扩容、ZDAL 连接池要重新评估……每一项都不能漏。

到了 11 月 10 号晚上，整个工区灯火通明。我第一次走进作战指挥室时，那种**几十台大屏并排、监控曲线在跳、各业务线 owner 戴着耳机在做指令同步**的画面，给我留下的震撼至今还在。和我之前在百度搜索做 VUI 渲染中台时见过的"应急响应"完全不是一个量级——**那是一种系统性的、有指挥、有节奏、有兜底、有 Plan B 的工程级仪式**。

零点开闸那一刻，TPS 曲线像火箭一样冲上去。我盯着自己负责的那条链路，看着限流配置精准生效、Tair 命中率维持在预期水位、xts 事务的悬挂监控曲线一路平稳——那种"自己设计的防御一项项被流量验证"的成就感，是任何其他工程场景都给不了的。

军规里第六条"生产变更"那一段——"提前计划、灰度分批、防御检测、变更观察、变更执行"——其实就是把双 11 作战那套节奏抽象成了日常变更的 SOP。**你只有真正经历过一次双 11 级别的作战，才知道为什么这五条规矩缺一不可**。

那种紧张又兴奋的感觉，我后来在九识第一次跟一辆 A 车型 在园区做封闭路测时又重新体验了一次——只是战场从屏幕换成了街道。

## 五、资金安全那一章，我读了三遍才真的懂

军规第三大类"资金安全"是我当年读得最认真的一章。三条：**资金风险、金额计算、核对设计、资金应急**。每一条背后我都能想起具体的故事。

### 「金额计算用 Money 类」——这条不是规范，是底线

新人有时会觉得"金额计算用 BigDecimal 就够了"。但军规要求的是**三元组**——"币种、amount、单位（元还是分）"。当年我们做核对的时候，真的见过研发在 DB 里存的是分、在接口里返的是元、在前端展示又转回分——没有出问题完全是运气好。

这件事在养老金业务里更敏感——养老金涉及多家基金公司、跨币种的场景虽然不多，但**精度问题在长期复利计算下会被放大**。我后来推动过一轮专项治理，把所有金额相关的 DTO 统一改成 Money 类的三元组，**这件事做完时整个链路的资金核对噪声直接降了一半**。

### 「过程终态均核对」——核对不是上线检查项，核对是日常基础设施

军规要求"过程和终态都要做核对，包括金额、状态、账户一致"。我自己后来总结了一句话：**"金融系统里没有'测试通过即上线'这件事，只有'核对持续通过即在线'这件事"**。

养老基金每天都要跑 N 套对账核对——业务流水对账、账户余额核对、过渡户流入流出自平衡、上下游清结算核对。任何一套核对一旦报警，业务方第一时间就要决策止损。**这套核对体系本身就是产品的一部分**，不是测试的副产品。

这种"核对即产品"的思维，到我后来在九识做 L4 级无人车的"全链路状态一致性核对"时还在用——**任务下发的状态、车端执行的状态、回传到云端的状态，三方任意时刻都得能对得上**。这其实就是养老基金那套核对思维的物理世界版。

### 「资金应急需双方复核」——这是一条人性的军规

最后一条"资金应急"我读的时候有种特别的感受——它谈的不只是技术，还是**人性**。

军规明确：**"应急订正必须有一方审批确认，调账涉及账户资金操作，需要谨慎，涉及用户账户调账必须有客满外呼确认。"**

这句话翻译过来是什么？是 **"在最紧张、最焦虑、最想立刻动手的那个时刻，我们要求工程师先停一下，确认两遍，再动手"**。这是金融级工程文化里我最敬重的一点——**它把人在压力下的认知偏差当成了一个必须被防御的工程变量**。

我自己后来无论是在菜鸟还是九识，遇到生产故障的应急操作，都会条件反射地问一句"这个动作有没有人复核过"。这是军规留给我的本能。

## 六、十年回看：这些规矩到底改变了我什么

我离开蚂蚁这些年，做过菜鸟的智能物流，又来到九识做无人配送车。业务形态从金融跳到物流再跳到自动驾驶，每一次跨越都隔着一道很大的鸿沟。但**军规里的那些底层规矩，居然一条都没过时**。

| 军规章节 | 最初学到的金融场景 | 后来在新场景里的体现 |
| --- | --- | --- |
| 并发控制 / 幂等 | 申购请求并发提交 | 物流面单生成幂等 / 无人车指令重发幂等 |
| 状态机推进 | 资金清结算状态流转 | 包裹状态流转 / 任务调度状态机 |
| 分布式事务 | xts + 本地补偿 | 跨系统订单状态最终一致 / 车云协同状态对齐 |
| 核对设计 | 资金对账 + 流入流出自平衡 | 物流台账核对 / 任务下发到车端到回传的三方核对 |
| 三板斧（可监控/灰度/应急） | 双 11 大促变更 | 物流大促变更 / OTA 灰度推送 |
| 应急三步（止血/复核/订正） | 资金事故应急 | 物流系统应急 / 无人车故障应急 |

这张表里每一行的"金融场景"和"新场景"看起来八竿子打不着——一个是数字世界的资金流，一个是物理世界的物体流——但**当我把"资金"换成"物体"或者"指令"，那套军规的逻辑就直接迁移过来了**。

这是我现在回头特别想跟当年那个第三周还在被"分布式事务悬挂"折磨得睡不着觉的自己说的：**这些规矩不是金融行业的规矩，是任何"对错误零容忍的复杂系统"都需要的规矩**。金融只是把它们最早、最完整地写下来了。

## 写在最后

那张军规海报现在大概还在原来那面墙上，也可能换了新的版本。我离开了，但那十二条规矩在我职业生涯里留下的痕迹，比我自己意识到的要深得多。

**它教我的不是"如何写出不出 bug 的代码"，而是"如何对一个会被真实世界使用的系统抱有持续的敬畏"**。

这种敬畏在我后来做菜鸟的智能物流、做九识的无人配送车时，一次又一次地救过我。每当我面对一个看似简单的需求、想"差不多就行"的时候，脑子里就会冒出当年新人串讲那天，主管放下咖啡杯问我的那句话——

> 你能不能在任意一秒回答出来：这笔钱现在到底归属于谁？

只是今天的版本可能变成了：

> 你能不能在任意一秒回答出来：这辆车现在到底应该停在哪里？

问题变了，但敬畏没变。这大概就是十二条军规给一个工程师最珍贵的东西。

> 写这篇文章的时候我特意翻了翻当年自己留下的几份评审记录、几次复盘文档。看到当时密密麻麻的评论和那些今天看起来都还成立的检查项，居然有点想笑——**那时候的自己虽然慌，但确实在认真长大**。
