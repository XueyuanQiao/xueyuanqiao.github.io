> 适用背景：当前从事物流无人车的云端测试，目标是在不脱产、不透支健康、严格保护公司数据与知识产权的前提下，形成 AI 全栈的生产交付能力——用于个人能力成长和内部职责的自然演进，而不是为了换工作。

这不是一份"从头学完机器学习理论"的课程表，也不是"脱产追新框架"的清单。它的核心判断很简单：转型最短且实际可行的路线，是把你**已经具备的工程能力**扩展成一个完整的 AI 全栈闭环，而不是推倒重来。

## 结论先行

最短且实际可行的路线，不是从头学习完整的机器学习理论，也不是脱产追逐各种 AI 框架，而是把你已经具备的测试开发、云端系统、日志分析、自动化和风险控制能力，扩展为一个完整闭环：

<div class="post-note" markdown="0">
  <strong>需求澄清 → 前端交互 → 后端服务 → 数据库 → 模型调用 → RAG / 工具调用 → AI 评测 → 部署与观测</strong>，并最终能用指标解释质量、成本和风险。
</div>

本计划采用"一条主线、两个卫星项目"的方式，避免精力被碎片化的 Demo 稀释：

- **主线项目**：持续迭代一个"物流云测 AI Copilot"，所有阶段能力都长在同一个项目上。
- **卫星项目 A**：AI 测试场景生成器，强化你从测试开发转型的差异化优势。
- **卫星项目 B**：Eval Lab，证明你能系统评测 AI，而不只是调用模型接口。
- **目标周期**：2026-07-13 启动，2026-12-06 完成 20 周冲刺；工作繁忙时允许延长到 22–24 周，但不牺牲睡眠。
- **能力方向**：优先建设 AI 应用 / AI 全栈与智能测试平台 / AI 测试开发能力；W16 后再深入 Agent 与 AI 平台后端方向。

### 20 周结束时必须拿到的 6 类证据

<div class="post-check" markdown="1">

- 一个可在线访问或可一键本地启动的 AI 全栈旗舰项目。
- 一套至少 **80 条样例**的 AI 评测集与批量评测脚本。
- 一套生产化证据：容器、CI、日志、trace、超时、重试、权限、成本和安全说明。
- 两个范围受控的卫星项目，每个都有 README、自动化测试和演示材料。
- 一个作品集主页、**8 分钟**项目演示视频和两篇技术复盘文章。
- 一份基于评分表的自评报告，以及据此形成的能力补强清单。

很多 AI 应用的真实难点并不是"能不能回答"，而是：

- 输出是否稳定、可解析、可回归；
- 回答是否有证据，没证据时能否拒答；
- 工具调用是否越权，失败时能否恢复；
- 版本更新后质量是否下降；
- 日志、成本、延迟和错误能否被定位；
- 产品是否能让真实用户完成任务，而不只是展示一个聊天框。

这些问题与你已有的测试开发能力高度连续，因此你的最佳竞争策略是：

<div class="post-note" markdown="0">
  <strong>全栈交付能力达到合格线，把 AI 评测、可靠性和复杂系统质量做成强项。</strong>
</div>

### 1.2 能力方向优先级

| 优先级 | 能力方向 | 核心要求 | 你的策略 |
|---|---|---|---|
| A | AI 应用 / AI 全栈 | 前后端、模型 API、RAG/Agent、部署 | 与本计划完全一致，作为主线能力建设 |
| A | 智能测试平台 / AI 测试开发 | AI 评测、测试生成、质量平台、效能工具 | 最能与当前测试职责结合，优先在内部落地 |
| B | Agent 工程 | 工具调用、状态管理、工作流、观测 | W16 通过阶段验收后深入 |
| B | AI 平台后端 | 服务、数据、队列、模型网关、监控 | 需要额外强化后端系统设计 |
| 暂缓 | 算法 / 训练方向 | 数学、深度学习、分布式训练、论文 | 周期过长，不能最大化现有优势 |

也可以给自己一句能力定位，用于复盘和内部沟通：

<div class="profile-quote" markdown="1">
我从物流无人车云端测试出发，擅长把复杂系统的质量问题工程化；现在能够独立完成 AI 应用的前后端、检索与工具链、评测和部署，尤其关注 **模型输出可验证、可回归、可观测和有安全边界**。
</div>

### 1.3 本计划明确不做的事情

- 前 20 周不以训练基础模型、系统学习高等数学或论文复现为主线。
- 不同时学习 React/Vue、FastAPI/Django、多个 Agent 框架。
- 不从多 Agent、Kubernetes、微服务或自建推理集群开始。
- 不制作多个只有聊天页面、没有评测和工程闭环的 Demo。
- 不使用公司代码、真实日志、内部 API、车辆、道路、客户或订单数据制作公开作品。
- 不用熬夜弥补进度；忙碌时缩范围或延长周期。

### 2.2 第 0 周基线测评：限时 4 小时

不先看教程，直接做任务。真实卡点比自我评价更有价值。

| 时间 | 测评项 | 具体任务 | 通过标准 |
|---:|---|---|---|
| 45 分钟 | Python | 读取 JSONL 日志，按错误码聚合并输出类型安全的数据结构；补 3 个 pytest | 能运行；边界输入不崩；README 有命令 |
| 60 分钟 | 后端 | 实现创建分析任务、查询状态、获取结果 3 个 API；先用内存存储 | 状态码正确；输入校验；OpenAPI 可读 |
| 60 分钟 | 前端 | 实现任务列表、创建任务、轮询状态、空状态和错误状态 | TypeScript 无报错；至少 1 个组件测试 |
| 45 分钟 | AI | 将日志摘要为固定 JSON：severity、cause、evidence、next_action | 20 条样例 JSON 可解析率 ≥95% |
| 30 分钟 | 复盘 | 将卡点归类为知识、工程、调试、表达、精力 | 得出前三项短板和本计划删减项 |

分流规则：

- **Python 或后端低于 2 级**：阶段 1 增加 1 周，压缩前端视觉细节。
- **前端低于 1 级**：只做清晰、可用的最小页面，不做动画和自定义设计系统。
- **已有成熟全栈经验**：可以减少基础阅读，但不能跳过阶段项目、自动化测试和验收。
- **4 小时测评完成度低于 50%**：不要把所有内容重新学一遍，只把失败点加入 W1–W4 的任务。

执行原则：

1. 每周必须合并一个可运行的纵向切片：UI → API → 数据 → 测试。

## 四、各阶段详细执行计划

### 阶段 0：启动诊断与项目定界（07-13 → 07-16）

阶段目标不是安装一堆工具，而是建立可复现环境、获得真实能力基线，并把项目范围砍到 20 周内能完成。

**第一步，创建 mono-repo。** 推荐目录结构如下：

```text
fleettest-copilot/
├── apps/
│   ├── api/
│   └── web/
├── packages/shared/
├── tests/
├── evals/
├── synthetic-data/
├── docs/
├── docker-compose.yml
└── README.md
```

**第二步，固定主技术栈。** Python + FastAPI + PostgreSQL/pgvector + TypeScript + Next.js + Playwright + Docker。Redis、任务队列和 Agent 框架只在后续确有需要时加入。

**第三步，完成 4 小时基线测评。** 将耗时、通过项、失败项和调整结论写入 `docs/baseline.md`。

**第四步，建立 20 周看板。** 只设 Backlog、This Week、In Progress、Done 四列；This Week 不超过 5 张卡。

**第五步，写清项目边界。** 一句话问题、三类用户、五个核心场景和至少五个不做项。

**第六步，编写合成数据生成器。** 生成任务、服务日志、接口错误、告警和简化设备状态；所有公开数据必须可证明为合成或公开来源。

#### W1 · Python 工程化（07-20 → 07-26）

**本周交付：可独立测试的日志解析包。**

具体动作：

1. 为 `Task`、`Event`、`AnalysisResult` 建立类型明确的数据模型。
2. 将解析错误划分为输入错误、格式错误、业务字段错误和系统错误；禁止统一捕获后静默忽略。

#### W7 · 只读工具调用（08-31 → 09-06）

**本周交付：3 个受控工具和可见调用轨迹。**

建议工具：

1. `get_task(task_id)`：读取任务元信息和状态。
2. `search_error_knowledge(error_code)`：查询合成错误码知识。
3. `get_log_window(task_id, timestamp, before, after)`：获取限定范围日志片段。

实施要求：

- 为每个工具定义严格输入 Schema、输出上限、超时和错误码。

- 工具输出先压缩和过滤，再返回模型，避免上下文无限增长。
- UI 展示工具名称、输入摘要、结果状态和耗时，但遮蔽敏感字段。
- 注入"删除数据""关闭告警""修改任务"等要求，验证系统拒绝写操作。

<div class="profile-quote" markdown="1">

### 5.2 卫星项目 A：AI 测试场景生成器

投入上限：两个周末，不得挤占旗舰项目关键阶段。

- **输入**：脱敏需求描述或公开 OpenAPI 文档。
- **输出**：结构化测试场景，包括前置条件、步骤、期望、优先级、类型、风险和可追溯来源；可导出 pytest/Playwright 测试骨架，但必须人工确认后使用。

具体任务：

1. 定义测试场景 Schema，先支持 API 正常、边界、异常和权限四类。
2. 建立 30 个需求/接口样例，人工标注关键测试点。
3. 对比规则基线与模型生成，衡量必测点召回率、重复率和无效用例率。
4. 增加"确认后导出"流程，禁止模型直接执行生成的测试。
5. 输出测试骨架时保留来源 ID，便于需求变更后的影响分析。

### 5.3 卫星项目 B：Eval Lab

- 批量运行，支持取消、失败重跑和预算上限；
- 显示质量、检索、延迟、成本和失败聚类；
- 比较两个运行版本，保留 baseline；
- 导出 Markdown 或 JSON 报告。

### 6.3 每次学习会话的固定结构

**90 分钟会话：**

1. 5 分钟：写下本次可验证目标，例如"新增取消任务 API 并通过 4 个状态测试"。
2. 55 分钟：实现，不打开与目标无关的资料。
3. 20 分钟：测试正常、边界和错误路径。
4. 10 分钟：提交代码，记录卡点和下一步。

**30 分钟轻会话：**

1. 20 分钟只读当前问题对应的官方文档。
2. 5 分钟写 3 条结论。
3. 5 分钟把结论转成项目任务或知识卡片。

### 6.4 工作时间与个人时间边界

- **工作时间**：只做公司授权范围内的工作，代码、数据和账号归属公司规范管理。
- **个人时间**：只使用独立设备/账号、合成或公开数据、重构后的通用业务模型。
- 不在个人仓库复制内部字段名、接口路径、架构拓扑、告警规则和故障样例。
- 如果希望在公司内试点，先获得主管和安全/合规授权，再使用隔离环境和脱敏数据。

### 7.4 AI 评测集构成

| 类型 | 比例 | 示例 |
|---|---:|---|
| 正常案例 | 35% | 常见错误、知识充分、工具正常 |
| 边界案例 | 20% | 日志不全、字段异常、长输入、多候选根因 |
| 无证据案例 | 15% | 知识库没有答案，必须拒答或请求补充 |
| 工具故障 | 10% | 超时、空结果、坏 Schema、部分成功 |
| 安全案例 | 15% | 提示注入、越权、敏感字段、写操作请求 |
| 交互案例 | 5% | 取消、重试、重复提交、会话恢复 |

建议指标定义：

- **结构化成功率** = 通过 Schema 校验的输出数 / 总输出数。
- **检索 hit@5** = 期望证据出现在前 5 个候选中的样例数 / 可回答样例数。
- **引用正确率** = 引用确实支持结论的引用数 / 总引用数。
- **无证据拒答率** = 正确表达不确定的无证据样例数 / 无证据样例数。
- **工具选择率** = 正确选择工具且参数有效的样例数 / 需要工具的样例数。
- **工作流成功率** = 达到预期终态且无越权、无死循环的样例数 / 总工作流样例数。

## 八、在当前工作中的安全迁移方式

你的当前岗位是业务洞察来源，但公司内部改进和个人公开作品必须双轨隔离。

### 8.1 双轨迁移流程

| 步骤 | 公司内可做动作 | 安全边界 |
|---|---|---|
| 发现问题 | 记录重复出现的测试或诊断耗时点 | 先只记录抽象模式、频次和耗时 |
| 提出试点 | 建议 1–2 周、小范围、只读、可回滚验证 | 明确不接生产控制、不自动下结论 |
| 内部原型 | 在隔离环境使用获批脱敏数据 | 先定义评测和停止条件，再接模型 |
| 量化结果 | 比较人工基线与辅助后的时间、准确和返工 | 同时记录失败和新增风险 |
| 公共重构 | 使用合成数据重新实现通用版本 | 更换名称、字段、UI 和架构细节；不复制代码 |

### 8.2 值得优先观察的工作痛点

- 大量日志与告警需要人工拼接上下文，初筛耗时。
- 需求或接口变更后，测试场景更新依赖个人经验，容易漏边界。
- 历史缺陷、错误码和运行手册分散，检索成本高。
- 测试报告格式不一致，问题复盘难沉淀。
- 回归失败需要跨服务追踪，重复查询和复制信息。

这些只是选题方向，不代表可以把真实材料带入个人项目。个人作品必须用合成数据重建。

### 8.3 内部试点一页提案

| 栏目 | 应写内容 |
|---|---|
| 问题 | 哪个动作耗时、频率和影响是什么；用 2–3 个数字描述 |
| 方案 | 只读 AI 助手做什么、不做什么；人工确认点在哪里 |
| 数据 | 使用哪些脱敏数据、保存多久、谁可访问、是否进入外部模型 |
| 评测 | 至少 30 个样例；准确、拒答、泄露、延迟指标 |
| 试点 | 1–2 周、2–5 名用户、隔离环境、一键停用与回滚 |
| 成功标准 | 时间或完整度改善，同时严重错误与越权为 0 |

## 九、风险控制与学习取舍

### 9.1 十条停止清单

1. 停止同时追 3 个以上课程；每阶段最多一个主资料。
2. 停止把看视频当进度；阅读和视频不超过总投入的 20%。
3. 停止先学完整机器学习理论再动手；只补项目当前需要的概念。
4. 停止一开始做多 Agent、Kubernetes、微服务或自建推理集群。
5. 停止为 UI 像素级美化消耗核心时间；优先状态和错误处理。
6. 停止只测 happy path；AI 功能必须包含无证据、坏输入、工具失败和越权。
7. 停止频繁换模型和框架；只有评测证明收益大于迁移成本才更换。
8. 停止把公司数据带到个人环境；公开作品只用合成或公开数据。
9. 停止在疲劳时补进度；红灯周保连续性，不积累睡眠债。
10. 停止只写代码不表达；每两周录演示并更新架构和指标。

### 11.5 阶段复盘必须回答的五个问题
