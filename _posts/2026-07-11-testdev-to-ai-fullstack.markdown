这份计划写给已经有测试开发、后端或质量平台经验，希望补齐 AI 应用全栈交付能力的人。

目标不是在 20 周内学完机器学习，也不是把简历改成“AI 全栈工程师”。更现实的目标是：独立做完一个范围受控的 AI 应用，能说明它怎样工作、怎样失败、怎样评测、怎样上线，以及哪些问题还没有解决。

计划按相对周次组织，任何时间都可以开始。每周建议投入 8—10 小时；工作繁忙时降到 5 小时，不用睡眠补进度。

<!-- more -->

## 最终要交付什么

主项目是一套 **质量事件助手**，只使用公开、合成或脱敏数据：

{% highlight text %}
测试运行 / 日志 / 变更说明
        ↓
结构化事件与证据
        ↓
检索 runbook、历史案例和接口文档
        ↓
生成摘要、候选原因和下一步检查
        ↓
只读工具查询任务、版本和指标
        ↓
评测、trace、成本和人工反馈
{% endhighlight %}

这个项目适合测试开发背景，因为它能复用已有的日志、自动化、风险和故障分析经验，同时覆盖完整 AI 应用链路。

不要使用公司源码、内部文档、真实日志、客户数据或生产凭据。作品集里的场景应重新建模，数据应当可公开。

## 技术栈怎么选

技术栈保持单一，避免把时间花在横向比较：

| 层次 | 建议 |
| --- | --- |
| 后端 | 当前稳定 Python + FastAPI + Pydantic |
| 前端 | TypeScript + React + Vite |
| 数据库 | PostgreSQL；需要向量检索时再加 pgvector |
| 模型 | 先接一个厂商，通过内部接口隔离 SDK |
| 模型能力 | 结构化输出、流式响应、函数工具 |
| 测试 | pytest、契约测试、Playwright |
| 观测 | 结构化日志 + OpenTelemetry trace |
| 交付 | Docker Compose、本地一键启动、CI、一个可访问环境 |

如果现有经验主要在 MySQL，也可以继续使用 MySQL，把向量检索放到独立服务。选型目标是完成项目，不是证明某个数据库更先进。

以 OpenAI 为例，新应用可以从 Responses API 做直接模型调用；当项目确实需要工具编排、handoff、guardrail 和 tracing 时，再评估 Agents SDK。其它模型厂商也采用相同原则：先用官方 SDK 建立清晰边界，框架只在复杂度真实出现后引入。

## 开始前的基线测评

用半天完成一个小功能：

> 上传一段合成测试日志，后端保存记录，调用模型输出符合 schema 的摘要，前端展示结果，并有一条自动化测试。

记录：

- 哪一层完全不会；
- 哪一层能做但很慢；
- 是否能独立排查错误；
- 是否知道怎样保存密钥；
- 是否有测试、日志和 README；
- 从零到运行用了多久。

20 周结束后再做一次同类限时任务。前后差异比课程证书更有说服力。

## 第一阶段：全栈底座（W1—W4）

### W1：后端工程

完成：

- 项目结构、依赖管理和配置分层；
- FastAPI 接口、Pydantic schema；
- 统一错误响应、日志和 request ID；
- pytest 单元测试；
- lint、类型检查和 CI。

交付：`POST /incidents` 能创建一条质量事件，并有成功、参数错误和重复请求测试。

### W2：数据库与任务状态

完成：

- PostgreSQL、迁移和事务；
- 事件、附件、分析任务、评测结果四类表；
- 幂等键和状态机；
- 一个独立 worker 处理后台任务；
- 失败重试和最大尝试次数。

不要一开始就上 Kafka、Kubernetes 或复杂队列。一个数据库任务表和单 worker 足够学习状态与恢复，出现真实瓶颈再替换。

### W3：前端纵向切片

完成：

- 事件列表、详情和创建表单；
- 加载、空状态和失败状态；
- TypeScript API 类型；
- 基础可访问性；
- 一条 Playwright 端到端用例。

UI 不必追求炫技。优先让用户能看清证据、状态和错误。

### W4：可复现与第一道门槛

完成：

- Docker Compose 一键启动；
- 示例数据和初始化脚本；
- README、架构图和 API 文档；
- CI 运行单测、类型检查和前端构建；
- 备份、重建数据库和基本安全说明。

阶段门槛：

- 新机器按 README 能启动；
- 创建、查询和状态流转可用；
- 自动化测试稳定重复运行；
- 仓库中没有密钥和内部数据。

门槛未达到，不进入模型功能。

## 第二阶段：模型调用与评测起步（W5—W8）

### W5：模型网关与结构化输出

在后端定义自己的 `ModelClient` 接口，业务代码不直接散落厂商 SDK 调用。

完成：

- 模型请求超时、重试和取消；
- 结构化输出 schema；
- 原始响应和解析结果分开保存；
- token、延迟和调用状态记录；
- mock 模型用于自动化测试。

第一个任务只做“日志摘要 + 证据列表”，不要同时做 RAG 和 Agent。

### W6：提示词版本与失败样例

完成：

- 提示词模板进入版本控制；
- 每个输出字段写清要求；
- 收集 30—50 条合成样例；
- 覆盖正常、缺日志、矛盾信息和恶意输入；
- 程序 grader 检查 schema、引用 ID 和禁止字段。

提示词变更必须能和评测结果关联。

### W7：语义评测

为无法用规则判断的部分编写 rubric，例如：

- 摘要是否遗漏关键错误；
- 是否区分事实和推测；
- 建议是否能从证据推出；
- 证据不足时是否表达不确定。

人工标注一小批样例，再用模型 grader 扩大执行。先测 grader 与人工的一致性，不一致的维度继续修改 rubric。

### W8：AI 纵向闭环

用户可以创建事件、触发分析、看到结构化结果、原始证据、模型版本和成本。

阶段门槛：

- 至少 50 条评测样例；
- 关键硬规则全部通过；
- 每次模型变更有逐样例差异；
- 模型不可用时任务可失败、重试和恢复；
- 前端不会把模型文本当作可信 HTML 直接执行。

## 第三阶段：RAG 与引用（W9—W12）

### W9：知识数据管道

准备公开或自写的 runbook、接口文档和故障案例。

完成：

- 文档来源、版本、权限和更新时间；
- 文本解析与分块；
- 去重和内容哈希；
- 删除、更新和重建索引；
- 文档片段可追溯到原文。

### W10：先做可解释检索

先建立简单基线：

- 关键词检索；
- 向量检索；
- 元数据过滤；
- Top-K 和最小相关度；
- 结果去重。

只有评测证明有必要时再增加混合检索、query rewrite 或 reranker。不要在没有基线时叠加组件。

### W11：检索与回答分开评测

检索评测：

- 必要文档是否被召回；
- Top-K 中无关片段比例；
- 过期或无权限文档是否出现。

回答评测：

- 是否被检索证据支持；
- 引用是否存在并可打开；
- 无证据时是否拒绝下结论；
- 是否把历史案例误写成当前事实。

### W12：RAG V1

质量事件助手能够引用 runbook 和历史案例，并在答案旁展示来源。

阶段门槛：

- 评测集扩充到 80 条以上；
- 关键问答都有可追踪引用；
- 检索失败和模型失败能分别定位；
- 权限过滤在检索前生效；
- 提示注入样例不会让系统越权读取或调用工具。

## 第四阶段：工具工作流与可靠性（W13—W16）

### W13：从确定性工作流开始

先接三个只读工具：

- 查询测试任务；
- 查询版本变更；
- 查询指标摘要。

工具使用 JSON Schema，参数在服务端再次校验。模型不直接访问数据库，更不能自行拼接 SQL。

### W14：安全与幂等

完成：

- 工具最小权限；
- 资源级授权；
- 超时、重试和熔断；
- 重复调用检测；
- 写操作默认不开放；
- 所有调用进入审计 trace。

如果要演示写操作，只能使用隔离 sandbox，并增加显式人工确认。

### W15：轨迹评测与故障注入

除了最终答案，还要评测：

- 是否选对工具；
- 参数是否正确；
- 是否少调用、错调用或循环；
- 工具超时、空结果和部分失败时怎样处理；
- 是否在证据不足时停止。

故障注入至少覆盖模型超时、数据库不可用、检索空结果、工具 429/500 和用户取消。

### W16：工作流 V2

交付一条可观察、可回放的完整流程：

{% highlight text %}
事件输入
→ 判断需要哪些证据
→ 调用只读工具
→ 检索 runbook
→ 生成候选原因
→ 输出缺失证据和下一步检查
{% endhighlight %}

阶段门槛：

- 每一步都有 trace；
- 工具调用可 mock、可回放；
- 无无限循环；
- 权限和安全样例全部通过；
- 关键结论明确区分事实、推测和建议。

## 第五阶段：上线、观测与作品集（W17—W20）

### W17：部署与发布

完成：

- 开发、测试、生产配置分离；
- 容器健康检查；
- 数据库迁移流程；
- CI/CD 与回滚；
- 一个受密码或访问控制保护的演示环境。

### W18：性能、成本和安全

做一次小型负载测试，观察：

- p50 / p95 延迟；
- 并发任务和队列积压；
- 单任务模型调用次数与成本；
- 超时、重试和降级；
- 大输入、恶意文件和提示注入；
- 日志与 trace 中是否泄露敏感信息。

### W19：项目说明

作品集至少包含：

- 问题与非目标；
- 架构图和关键数据模型；
- 三个重要架构决策记录；
- 评测集设计和逐版本结果；
- 安全、成本和失败边界；
- 两个真实 bug 的复盘；
- 5—8 分钟演示视频。

不要只录“成功路径”。展示一次工具失败、模型拒答或回滚，更能说明工程能力。

### W20：综合验收

重新做开始前的限时任务，并完成一次陌生需求：

> 新增一个只读工具，让系统查询发布记录，并把工具选择、参数、权限、评测和 UI 一起交付。

最终门槛：

- 能在 90 分钟内说清需求、风险和最小纵向切片；
- 能独立修改前端、后端、数据库和模型层；
- 能写出确定性测试与 AI 评测；
- 能从 trace 定位失败层；
- 能说明何时不用 RAG、Agent 或更大模型；
- 能在不泄露公司信息的前提下公开项目。

## 每周时间安排

一个可持续模板：

| 时间 | 内容 |
| --- | --- |
| 工作日 2 次 × 60—90 分钟 | 学习当前周必需知识，并完成小改动 |
| 周末 1 次 × 3 小时 | 做纵向功能和集成 |
| 周末 1 次 × 60 分钟 | 测试、文档和复盘 |

采用三档模式：

- **绿灯周（8—10 小时）**：按计划推进；
- **黄灯周（5—6 小时）**：只完成主交付，不扩展工具；
- **红灯周（2 小时以内）**：修测试、整理问题、保持项目可运行。

红灯周不补债。下周重新排优先级，必要时把 20 周延长。

## 每周复盘只回答五个问题

{% highlight markdown %}
## 第 N 周

1. 本周交付了什么可运行证据？
2. 哪个假设被证明是错的？
3. 目前最大的质量或安全风险是什么？
4. 下周唯一必须完成的纵向切片是什么？
5. 应该删掉哪项计划？
{% endhighlight %}

## 十条停止清单

1. 不同时接三家模型；
2. 不在没有评测集时调提示词；
3. 不先搭多 Agent；
4. 不为一个作品集引入 Kubernetes；
5. 不把向量数据库当成 RAG 的起点；
6. 不让模型直接执行任意 SQL 或 shell；
7. 不使用真实公司数据；
8. 不把模型 grader 当成绝对真相；
9. 不用熬夜补计划；
10. 不用代码行数、课程数和工具清单判断完成度。

## 关于评测工具的选择

评测数据、grader 和逐样例结果应保存在自己的仓库或数据存储中，厂商平台只作为运行和展示工具。

这是一个现实的工程要求：工具会改版或下线。OpenAI 官方文档已经公布旧 Evals 平台将在 2026 年 10 月底进入只读，并计划于 11 月底关闭。无论使用哪家服务，都不要让评测资产只能从某个网页里查看。

一个简单的本地 runner + JSONL 数据 + CI 报告，通常比先选大型评测平台更可靠。

## 20 周之后

完成这份计划，只能证明你做过一次相对完整的 AI 应用交付。它不能代替生产经验，也不能自动改变岗位。

下一步可以根据实际反馈选择一个方向深入：

- AI 应用后端与平台；
- RAG 和知识工程；
- Agent 可靠性与安全；
- AI 评测与质量工程；
- 前端交互与人机协作；
- 模型推理、训练或数据工程。

测试开发的优势不在于“更会找模型错误”，而在于习惯追踪证据、设计失败场景、建立回归和守住发布边界。把这部分能力带进全栈交付，比重新包装一个 title 更有长期价值。
