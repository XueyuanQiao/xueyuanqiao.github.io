# 博客性能优化方案

> **第一前提（硬性约束）**：任何优化都**不得影响当前任何页面的呈现与交互，必须对用户完全无感**。
> 一旦某项改造可能引入白屏闪烁（FOUC）、字体切换跳动（FOUT）、布局位移、动画差异或交互行为变化，且无法确保"用户感知不到"，则**宁可保留性能问题也不做处理**。
>
> 对象仓库：`xueyuanqiao.github.io`（自定义主题的 Jekyll 博客）
> 说明：本文档仅为方案说明，未对仓库代码做任何修改。

---

## 判定原则

在"零用户可感知影响"前提下，把四项候选改造重新分为两类：

| 类别 | 判定 | 含义 |
|---|---|---|
| ✅ 安全改造 | 满足前提 | 纯后端/构建层变化，输出的字节语义等价，用户看到的页面与交互**逐像素、逐行为一致** |
| ⚠️ 受限改造 | 有感知风险 | 会改变渲染时序或字体呈现，**可能被用户察觉**；在本前提下**降级为可选项或直接不做** |

结论速览：

| 优先级 | 事项 | 前提判定 | 处理建议 |
|---|---|---|---|
| P0 | aurora.css **压缩（minify）** | ✅ 安全 | **做**（构建期原地压缩，不改路径） |
| P0 | aurora.css **关键 CSS 内联 + 其余异步** | ⚠️ FOUC 风险 | **不做**（无法保证无感） |
| P0 | site.js **压缩（minify）** | ✅ 安全（需回归验证） | **做**（构建期原地压缩，不改路径） |
| P1 | 资源版本号改用**内容哈希** | ✅ 安全 | **做**（最稳的纯收益项） |
| P1 | 首页字体**异步加载** | ⚠️ FOUT 风险 | **降级**：只做无感子集（preconnect / 自托管 + preload），不做会引入字体跳动的裸异步 |

---

## 一、✅ 安全改造（满足"无感"前提，建议实施）

### A1 · aurora.css 压缩（minify）

**问题**
- `assets/css/aurora.css` 为 **307KB / 11229 行**，完全未压缩。
- 在 `_layouts/default.html` 中渲染阻塞引入，几乎所有页面首屏都要等它下载解析完。

**为什么无感**
- Minify 只删除空白、注释、合并等价写法，**不改变任何一条样式规则的语义**。压缩前后浏览器计算出的样式完全一致，页面呈现逐像素相同，动画、`prefers-reduced-motion` 逻辑均不受影响。

**改造方案（保持"零感知"的关键：不改变加载方式、不改变文件路径）**
- 采用**构建期原地压缩**，让产物仍是同一个 URL（`/assets/css/aurora.css`），模板一行都不用动：
  - 方案一（推荐，插件级、路径不变）：引入 `jekyll-minifier`，构建时自动压缩 CSS/JS/HTML，产物路径与现在完全一致。
  - 方案二（零新增依赖）：将 `aurora.css` 改为经 Jekyll Sass 处理并设置 `sass: { style: compressed }` 输出压缩结果。
- **仍保持渲染阻塞引入方式不变**——这一点是刻意的：不动加载时序 = 不引入任何 FOUC 风险。收益来自"同样的时序、更少的字节"。

**预期收益**
- 纯压缩通常 307KB → ~220–250KB；叠加服务端 gzip/brotli 后传输体积可降到 ~40–60KB 级别。关键渲染路径字节数下降，FCP/LCP 改善，且用户完全无感。

**验证**
- [ ] 压缩前后随机抽查若干页面，视觉与交互逐一比对无差异。
- [ ] 确认 `@media (prefers-reduced-motion)` 等媒体查询块未被压缩破坏。

---

### A2 · site.js 压缩（minify）

**问题**
- `assets/js/site.js` 为 **168KB / 4426 行**，未压缩。
- 加载方式本身已是合理的：`default.html` 底部通过 runtime-loader 以 `async` 动态注入，不阻塞渲染。但 168KB 的下载/解析/执行仍推迟可交互时间（TTI）。

**为什么（基本）无感**
- Minify（含变量名 mangle）在绝大多数情况下语义等价，交互行为不变，用户无感。
- 需留意的边界：该脚本较复杂（音乐播放器、`AudioContext`、拖拽、PJAX 等）。极少数依赖函数名 / `Function.prototype.toString` 的写法在 mangle 后可能异常。因此归类为"安全但需回归验证"。

**改造方案（保持"零感知"：路径不变、加载方式不变）**
- 同样用**构建期原地压缩**（`jekyll-minifier` 或 CI 里 `terser`），产物仍指向现有路径，runtime-loader 无需改动。
- 保留未压缩源用于调试；如担心 mangle 风险，可先只做 `compress` 不做 `mangle`，收益略小但更保守。

**预期收益**
- 168KB → ~90–110KB；gzip/brotli 后 ~30–40KB。TTI 提前，交互更快就绪。

**验证（务必逐项回归，确保交互零变化）**
- [ ] 主题切换（暗/亮，记忆）
- [ ] 移动端侧边栏抽屉、遮罩、焦点管理
- [ ] 站内搜索（命令面板、键盘导航）
- [ ] 音乐播放器：播放/暂停/切歌/拖拽/贴边/可视化/跨页续播
- [ ] 滚动渐显、阅读进度、回到顶部、目录高亮
- [ ] PJAX 页面切换、代码块复制

### A3 · 资源版本号改用内容哈希（恢复长期缓存）

**问题**
- 多处使用构建时间做缓存版本号：`{% assign asset_version = site.time | date: '%s' %}`，以 `?v={{ asset_version }}` 挂在 CSS/JS 上（`default.html`、`particle-cat.html`、`service-worker.js` 等）。
- `site.time` **每次构建都变**，即使 `aurora.css` / `site.js` 内容未变，版本号也变。

**影响**
- 每次部署后，回访用户的相关缓存全部失效，被迫重新下载 aurora.css（307KB）+ site.js（168KB）等，无法利用长期缓存。

**为什么无感（且是纯收益）**
- 版本号规则的改变**不改变任何页面内容与交互**，用户看不到差异。
- 内容变了 → 哈希变 → URL 变 → 用户自动拿到新文件（与现在一样保证"最新"）；内容没变 → 哈希不变 → 命中缓存（这是收益）。**既不会拿到旧内容，也没有任何视觉/交互变化**，是四项里感知风险最低的。

**改造方案**
- 将 `?v=构建时间` 改为 `?v=文件内容哈希`：
  - 方案一（Liquid 原生）：读取文件内容做 `md5` 作为版本号，例如对可被读取的样式/脚本：
    ```liquid
    {% capture css_raw %}{% include_relative assets/css/aurora.css %}{% endcapture %}
    {% assign css_ver = css_raw | md5 %}
    <link rel="stylesheet" href="{{ '/assets/css/aurora.css' | relative_url }}?v={{ css_ver }}">
    ```
    （视文件是否可被 `include_relative` 读取而定，必要时改放 `_includes/` 或用方案二。）
  - 方案二（更稳）：用 `jekyll-assets` 或 CI 生成带指纹文件名（如 `aurora.a1b2c3.css`），对这类文件配置强缓存 `Cache-Control: max-age=31536000, immutable`（需部署平台支持自定义响应头）。

**注意（不影响用户体验，但需正确区分）**
- `service-worker.js` 中的音频缓存版本 `MUSIC_CACHE` 由 `music_cache_version` 独立控制，与本项无关，**不要合并**，以免影响音乐缓存与跨页续播体验。

**预期收益**
- 未变更资源回访命中缓存，实现"零重复下载"，带宽与加载时间双降，用户无感。

## 二、⚠️ 受限改造（存在用户可感知风险，在本前提下不做或降级）

### B1 · aurora.css 关键 CSS 内联 + 其余异步 —— 在本前提下【不做】

**性能上的诱惑**
- 提取首屏关键 CSS 内联进 `<head>`，其余 307KB 异步加载，可显著提前首屏。

**为什么与"无感"前提冲突**
- 关键 CSS 一旦提取不完整，会出现**首屏样式闪烁（FOUC）**：用户先看到无样式/半样式内容，随后跳变为完整样式。这是**明确可被用户感知**的体验回退。
- 该站视觉高度定制（大量背景动画、渐变、`backdrop-filter`、卡片 3D 等），关键 CSS 边界极难精确切割，FOUC 风险高。
- 异步加载改变了 CSS 到达时序，本质上就在赌"用户注意不到中间态"，与前提直接冲突。

**结论**
- **不实施。** 保留 aurora.css 的渲染阻塞加载方式，仅通过 A1 压缩获取无感收益。若未来确有必要，须先在预发环境用真实机型反复验证"无任何可见闪烁"后再评估。

---

### B2 · 首页字体异步加载 —— 在本前提下【降级为无感子集】

**现状**
- 首页 `/`（`particle-cat.html`）字体为渲染阻塞引入，且请求了 `400;500;600;700` 四档：
  ```html
  <link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=JetBrains+Mono:wght@400;500;600;700&display=swap">
  ```
- 对比 `default.html` 已用 `preconnect + media="print" onload` 异步模式，且只请求 `400;600` 两档。

**为什么"裸异步"与前提冲突**
- 首页是 monospace 主导的设计。把字体改为异步后，会先用系统回退字体绘制、再切换到 JetBrains Mono，产生**字体跳动 / 字宽变化 / 轻微布局位移（FOUT）**。这类切换在等宽排版下尤其显眼，**用户可感知**，与前提冲突。
- 因此**不采用会引入可见字体切换的裸异步方案**。

**降级方案：只做"用户无感"的字体优化子集**
1. **补齐 `preconnect`（完全无感、纯提速）**：
   ```html
   <link rel="preconnect" href="https://fonts.googleapis.com" crossorigin>
   <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
   ```
   仅提前建立连接，不改变任何渲染时序与呈现，零感知。
2. **自托管字体 + 预加载（推荐，最接近"无感提速"）**：
   - 将 JetBrains Mono 需要的字重放入 `assets/fonts/`，用 `@font-face` 本地引用，并 `preload` 字体文件：
     ```html
     <link rel="preload" as="font" type="font/woff2"
           href="{{ '/assets/fonts/JetBrainsMono-Regular.woff2' | relative_url }}" crossorigin>
     ```
   - 字体在首屏前就绪，切换窗口趋近于零，用户几乎无法察觉；同时摆脱第三方字体 CDN（国内更稳）。
   - 关键：**自托管的必须是与线上完全相同的字体**，保证呈现逐像素一致。
3. **字重精简（仅在可证明未使用时才做，否则视为可感知）**：
   - 已核验 `particle-cat.css` 实际使用的 `font-weight` 为 `520 / 580 / 600 / 620`（浏览器会就近取整到已加载的 500/600），未见 `700`。
   - `700` 档**疑似未使用**，但必须先全量核验（含 `font:` 简写、`bold`、内联样式、JS 动态设置）确认无任何元素依赖，方可移除；否则移除会导致这些元素字重变化，**属可感知**，不做。

**结论**
- **只实施第 1 项（preconnect），第 2 项作为推荐的无感提速项，第 3 项以"证明未使用"为前置门槛。**
- **不实施**会引入可见字体切换的裸异步替换。

## 三、落地顺序与总验证清单

**建议顺序（全部满足"无感"前提）**
1. **A3 内容哈希版本号** —— 感知风险最低的纯收益，先落地。
2. **A1 aurora.css 压缩**（构建期原地压缩，路径与加载方式不变）。
3. **A2 site.js 压缩**（构建期原地压缩，随后按清单逐项回归交互）。
4. **B2 降级子集**：补 `preconnect`；如推进自托管字体，务必确保字体文件与线上一致。
5. **B1 一律不做**（FOUC 风险，违背前提）。

**总验证清单（核心目标：用户零感知）**
- [ ] 改造前后同一页面截图逐像素比对，无视觉差异。
- [ ] A2 后按 A2 小节的交互清单逐项回归，行为无任何变化。
- [ ] 二次访问时，未变更的 CSS/JS 命中浏览器缓存（Network 面板 URL 未变、`from disk/memory cache`）。
- [ ] 首页字体呈现无可见跳动；若自托管，确认字形与线上一致。
- [ ] 音乐跨页续播、`service-worker` 音频缓存不受版本号改造影响。
- [ ] Lighthouse / WebPageTest 对比改造前后 FCP / LCP / TTI（应改善或持平，且无体验回退）。

> 本文档为方案说明，未对仓库代码进行任何修改。所有建议均以"用户无感"为不可逾越的前提；凡无法确保无感的优化，均已标注为不做或降级。
